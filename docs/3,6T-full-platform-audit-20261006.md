# تقرير التدقيق الشامل لمنصة 3,6T — المجالات خارج HCM

**تاريخ التقرير:** 2026-10-06  
**النطاق:** تجميع ومراجعة رئيسية لنتائج 15 تدقيقًا مستقلًا للمجالات **غير الخاصة بـHCM**.  
**مصادر التجميع:** التقارير تحت `docs/audit-non-hcm-20261006/` ونتائج الاختبار والأدلة المذكورة فيها.  
**طريقة الحكم:** مراجعة أدلة موثقة؛ لم يُعاد في هذا التقرير تشغيل الحزم، ولم تُنشأ اتصالات خارجية أو نشر أو تغيير إعدادات تشغيلية.

> **الحكم التنفيذي:** النتيجة الإجمالية هي **غير جاهز للتشغيل المؤسسي أو لمعالجة بيانات/أموال/التزامات حقيقية من طرف إلى طرف**، رغم وجود نوى محلية واسعة ومحكومة في المجالات الخمسة عشر. متوسط الدرجات غير المرجح هو **6.1/10** (`92.1 ÷ 15`)، وليس نسبة اكتمال ولا نسبة نجاح اختبار.
>
> **قاعدة الدليل الحاكمة:** وجود ملف كود أو migration أو API أو واجهة RTL، وكذلك نجاح فحص صياغة أو فحص ساكن، **لا يساوي** قبول مالك العملية، أو UAT، أو جاهزية إنتاج، أو تكاملًا خارجيًا، أو تنفيذًا نظاميًا/ماليًا فعليًا. كما أن السجل المحلي أو CSV أو «توثيق فعل خارجي» لا يتحول إلى بنك أو مزود فوترة أو توقيع إلكتروني أو جهة حكومية بمجرد وجوده في المنصة.

### حدود الخريطة

- الخريطة تصف **ما أثبتته التقارير من وحدات محلية ومسارات وقيود**؛ لا تقيس عدد الصفحات ولا حجم الكود ولا تعلن اكتمال المنتج.
- تتميز البنية بوجود مسارات HTTP وواجهات SPA وقيود SQL وسجلات تدقيق في نطاقات عديدة، لكن تلك الطبقات لا تثبت أن البيانات الحاكمة والسياسات والملاك والتشغيل اليومي موجودون أو مقبولون.
- لا تتضمن هذه الخريطة ادعاء وجود اتصال بـ **Zoho أو Resend أو DNS**، ولم يتم في هذا التدقيق نشر المنصة أو إجراء أي اتصال بها.

## 3. ما هي نقاط القوة الفعلية؟

1. **عمق ضبط محلي متكرر:** يظهر في أغلب المجالات فصل المعدّ/المعتمد/المتحقق، انتقالات حالات، immutability أو append-only في السجلات المهمة، optimistic versioning، tenant isolation، وقيود SQL لا تعتمد على الواجهة فقط.
2. **ربط منتج ملموس:** توجد وحدات خادم وmigrations وواجهات SPA ومسارات HTTP مسجلة لمجالات مالية وتجارية ومشاريع وخدمات وتعاون وتقارير وGRC، وليست النتائج مجرد ملفات تصميم منفصلة.
3. **دورات أعمال محلية واسعة:** الدفتر وAP/AR، CRM إلى مشروع، طلبات الشراء، الاستلام والوقت والإقفال، كتالوج الخدمة، الملفات والنماذج، وتقارير snapshots تقدم قاعدة بناء جيدة للتطوير المؤسسي لاحقًا.
4. **نزاهة الدليل داخل المنصة:** تكررت البصمات، النسخ، التصحيحات كسجلات لاحقة بدل مسح الأصل، وربط الدليل بالسجل، وحجب الأرقام غير المتاحة بدل اختراع أصفار في EPMO والتقارير.
5. **الوعي بحدود المنتج في مواضع عديدة:** تقارير E01 تعلن unavailable/unmeasurable، وبعض الوحدات تصرح أن الدفع أو الفوترة أو القبول الخارجي يدوي/توثيقي. هذا أفضل من ادعاء اتصال غير موجود، لكنه لا يغلق الفجوات.
6. **إشارات تحقق إيجابية محددة فقط:** منها 47/48 في حزمة مشتريات محددة، و3/3 في واجهة workspace، و11/11 في report figures/cockpit UI، و2/2 لمزود AI الوهمي، ونجاحات جزئية ظاهرة في Node24 لبعض الحزم. تلك أدلة نقطة محددة، وليست شهادة منصة أو قبول إنتاج.

## 4. نقاط الضعف والحواجز المشتركة

### 4.1 حواجز تشغيل وإنتاج مشتركة

1. **منع الإنتاج مقصود وصريح:** README/MANUS والخادم يصفون التطبيق محليًا/مصطنعًا؛ ويُرفض `NODE_ENV=production` في المواضع المشار إليها. لا يجوز فتح الخدمة على الشبكة أو تجاوز هذا الحظر باعتباره «إطلاقًا».
2. **بيئة الاختبار غير موحدة:** المشروع يتطلب Node 24.x متوافقًا (وأشير إلى 24.21.0)، بينما أخفقت حزم كثيرة في Node 22.13.0 قبل assertion عند `no such module: fts5`. هذا ليس فشل منتج مثبتًا، **ولا نجاحًا**؛ إنه مانع لإصدار حكم تحقق قابل لإعادة الإنتاج.
3. **لا قبول ملاك عملية مكتمل:** نصوص قبول وتوجيهات UAT موجودة في مجالات متعددة، لكن التوقيع/المالك/النتيجة/القيود غير معبأة أو غير موثقة. لا يصح استبدال قبول المالك بنتيجة unit test.
4. **الضوابط والسياسات المرجعية غير مكتملة:** حدود التفويض، التقويم، أسعار/مراحل pipeline، SLA، windows، قوالب خطابات، تعريفات KPI، وبيانات الدليل المرجعي تحتاج مالكًا وإصدارات واعتمادًا وتطبيقًا فعليًا.
5. **غياب بنية تشغيل مؤسسية:** لا SSO/SCIM، ولا secrets vault أو مراقبة مركزية أو alerting/SLO/HA، ولا نسخ خارج الجهاز غير قابلة للتعديل أو RPO/RTO وتمارين restore متكررة مثبتة.

### 4.2 حدود التكامل الخارجي والدليل النظامي

- **المالية/البنك/الدفع:** لا Open Banking ولا تنفيذ تحويل أو تحصيل؛ مطابقة CSV وسجل «تنفيذ يدوي» لا يساوي حركة مصرفية مثبتة.
- **الفوترة والضرائب:** بوابة e-invoice disconnected؛ لا XML أو شهادة/مفتاح أو إرسال أو رد جهة. VAT/Zakat/withholding أوراق عمل محلية وليست تقديمًا رسميًا.
- **المبيعات والعميل:** سجل قبول عميل أو طباعة تقرير ليس بوابة عميل أو e-sign أو تحقق هوية أو إثبات إرسال رسمي.
- **التوريد:** PO `internal_only` وليس أمرًا مرسلًا للمورد؛ دعوة RFQ، الدفع البنكي وإشعار تغيير الحساب ليست تكاملات منفذة.
- **الاتصالات والتعاون:** لا inbox أو إشعارات قابلة للتنفيذ لمعظم أحداث التعاون؛ ولا بريد/Teams/Basecamp أو تخزين كائنات موثق.
- **الذكاء الاصطناعي:** اختبارات المزود الوهمي لا تثبت عقد مزود أو DPA أو موقع معالجة أو egress allowlist أو تعاملًا آمنًا مع بيانات حقيقية.

## 5. تصنيف الجاهزية: قابل للاستخدام محليًا، جزئي، وغير جاهز طرفيًا

### 5.1 خدمات قابلة للاستخدام **محليًا فقط** وبحدود صريحة

ليست هذه خدمات إنتاجية أو معتمدة لبيانات حقيقية. يمكن استخدامها في بيئة development/staging مع بيانات اصطناعية ومالك فني لمراجعة السلوك:

- دفتر SAR المحلي، قيود متوازنة، الأستاذ وميزان المراجعة، AP/AR، المطابقة البنكية من CSV، وقوائم الإقفال/الضرائب كأوراق عمل.
- CRM محلي، pipeline، التقديرات والتسعير، proposal of record، مراجعة EPMO وعروض محفوظة بإصدارات.
- intake للمشاريع، محاور التنفيذ، الحجوزات والسعة، كشوف الوقت، إقفال المشروع، وإصدار E01 الذي يعلن فجوات القياس.
- دورة شراء داخلية وRFQ/ترسية/استلام وفواتير مورد محلية، بشرط عدم تصوير PO أو الدفع أو الفاتورة كتنفيذ خارجي، وبعد إصلاح واجهة RFQ.
- كتالوج الخدمات والطلبات والموافقات والإسناد والإغلاق وعقود مخرج محددة، بشرط إعداد الخدمة والمهل يدويًا ومراقبة العمل يدويًا.
- مساحة التعاون وملفاتها في الاستخدام المختبري فقط؛ **لا تنزيل ملفات إنتاجي قبل AV/quarantine**.
- حملات واستوديو وصرف إعلامي وإنتاج وشهادات كدفاتر تشغيل داخلية/اختبارية، لا كمصدر مقاييس أو نشر خارجي مثبت.
- تقارير محلية وsnapshots وCSV/XLSX/طباعة متصفح، لا كحزمة BI رسمية أو توزيع تنفيذي مجدول مؤكد.
- نماذج وخطابات ومرفقات في الوضع المحلي، مع منع استخدام policy library الخاصة بين المستأجرين حتى معالجة العزل.
- سجلات GRC والخصوصية ومراجعات الوصول، مع اعتبارها سجلات عمل وليست إثبات امتثال قانوني مكتمل.
- TOTP/RBAC/CSRF وbackup/restore المحلي كضوابط تطويرية، لا كبديل IdP/DR مؤسسي.

### 5.2 خدمات جزئية ذات نواة قوية ولكنها ليست جاهزة للاعتماد التشغيلي

| المجال | لماذا هو جزئي؟ |
|---|---|
| المالية والفوترة | الضبط المحاسبي المحلي واسع، لكن دورة النقد/الضريبة/الفاتورة والدفع لا تخرج من المنصة ولا تملك تشغيلًا مؤسسيًا مثبتًا |
| المبيعات والمشاريع | دورة من فرصة إلى مشروع موجودة، لكن البيانات الحاكمة، قبول مالك، العميل الخارجي، التوقيع/التوزيع، ومقاييس EPMO مكتملة جزئيًا فقط |
| المشتريات | الضوابط الخلفية قوية نسبيًا، لكن UI RFQ متراجع، والـPO/الدفع/الفاتورة الخارجية ليست منفذة |
| إدارة الخدمات | نموذج طلبات جيد، لكن alerts وSLA والقيم المعتمدة والتكاملات غير متحققة |
| التعاون | نموذج وصول ومحتوى جيد، لكن فجوة UI/API وغياب notifications/AV/recurrence تمنع الاعتماد اليومي الآمن |
| BI والتقارير | snapshots وحماية التفصيل موجودة، لكن لا اتجاه KPI تاريخي ولا worker متين ولا UAT executive |
| AI والمعرفة | ضوابط واختبارات وهمية محلية موجودة، لكن المحتوى والحوكمة الخارجية والاحتفاظ وإيقاف الأصل المتأخر غير كافية |
| الأمن والمنصة | توجد ضوابط تطبيق محلية، لكنها لا تحقق baseline مؤسسيًا مع MFA مفروض وSSO وDR وobservability |

## 8. خطة الإغلاق حسب الأولوية

### P0 — موانع صارمة قبل أي بيانات/تشغيل حقيقي

1. **إيقاف ادعاءات الجاهزية أو الامتثال أو التنفيذ الخارجي:** وسم واضح لكل مسار محلي/يدوي/disconnected/internal-only، ومنع أي تسويق أو قرار يعتمد الفاتورة أو البنك أو الضريبة أو التوقيع أو العميل الخارجي كأنه منفذ.
2. **إصلاح عزل مكتبة السياسات فورًا:** تطبيق `tenant_id = ? OR tenant_id IS NULL` بصورة موحدة في كل قراءات libraryHome/libraryIndex/findArticle/searchLibrary/articleView/adminBoard، وكتابة اختبارات تسرب سلبية متعددة المستأجرين، وتعطيل النشر متعدد المستأجرين حتى نجاحها.
3. **حجب الملفات الإنتاجية حتى AV/quarantine:** ربط نتيجة مسح فعلية بإصدار الملف؛ لا تعتمد وسم `clean` مصدره متغير بيئة بلا دليل ماسح؛ منع التنزيل إلى أن ينجح المسح.
4. **فرض baseline أمني:** MFA للحسابات والقدرات الحساسة، enrollment وخطة break-glass مدققة، إيقاف الوصول الحساس بكلمة مرور فقط، وخطة هوية مؤسسية SSO/OIDC/SAML وlifecycle قابلة للتدقيق.
5. **تصحيح corpus السياسات/المعرفة:** استلام الأصول الموقعة، بصمها ومطابقة النصوص الـ127، اعتماد المحتوى والمالك القانوني؛ حجب استعماله في policy assistant أو قرارات امتثال حتى ذلك.
6. **AI fail-closed:** إيقاف كل مساعد محلي وخارجي عند انتهاء مراجعة الأصل/الحوكمة، واختبار الإيقاف أثناء التشغيل؛ حظر provider حي وبيانات حقيقية قبل DPA وموقع المعالجة وegress/redaction/retention.
7. **توحيد بيئة الدليل:** تثبيت Node 24.21.0 (أو النطاق المتوافق الموثق) وSQLite بـFTS5، قاعدة اختبار نظيفة، worker محدود التوازي، SHA/versions/migrations/TAP نهائي كـartifact. لا تفسر إخفاق Node22 على أنه نجاح أو فشل وظيفي.
8. **DR خارج الجهاز:** نسخة مشفرة/immutable مع مفتاح منفصل وretention وRPO/RTO وتمرين restore موثق؛ لا يُعد `VACUUM INTO` محليًا وحده تعافيًا مؤسسيًا.

**بوابة P0 للخروج:** لا بيانات حقيقية، لا نشر، لا اتصال بمزود، ولا رفع ادعاء خارجي قبل إغلاق البنود أعلاه وتوقيع مالك الأمن/القانون/البيانات على حدود النسخة.

### P1 — إكمال الدورات التشغيلية وUAT المنضبط

1. **مالية وتجارية:** اعتماد دليل الحسابات والتقويم والتفويض والتوقع/التحصيل والضريبة؛ UAT صناعي لمسار بنك→تسوية→إقفال/فتح وAP/AR/VAT، ولـCRM→تقدير→عرض→اتفاق→مشروع. حسم الربط بين recurring draft وAR/invoice والعملة والاستثناءات.
2. **تكاملات خارجية فقط بعد قرار نطاق:** لكل بنك/دفع/e-invoice/ضريبة/e-sign/portal/مورد/إعلان أو CRM: owner، source of truth، عقد، sandbox، external ID، idempotency، reconciliation، secrets vault، مراقبة وrunbook وUAT. أو توثيق صريح بأنها خارج النطاق والعملية يدوية.
3. **المشاريع وBI:** بناء observations تاريخية وتعريفات/أهداف/حدود KPI قابلة للإصدار والاعتماد؛ قياس السعة والساعات أولًا ثم الربحية والذمم والخدمات؛ worker/queue durable للجدولة مع retry/alert؛ UAT CEO/CFO/ملاك البيانات.
4. **المشتريات:** إصلاح `rfqPanel`، إعادة الاختبار واللقطات، اعتماد سقف الدفعة الأولى ومهلة تغيير الحساب، وقبول المشتريات والمالية؛ منع وصف PO الداخلي كإرسال.
5. **الخدمات والدعم:** إعداد service owner والجمهور/الأهلية/SLA/window/output contract؛ تنفيذ readers/enforcers وتنبيه idempotent لـunclaimed/due/overdue/escalation، وإضافة مسار refund أو قرار رسمي لحاجز offboarding.
6. **التعاون والوثائق:** إكمال UI/API، inbox/deep links، recurrence أو تعديل الوعد، قيود check-in، تنزيل/إصدار/دليل ملفات بعد AV، قوالب الخطابات بمسودة–مراجعة–نشر، وخيار e-sign قانوني إذا تطلبه المالك.
7. **الخصوصية/GRC:** الأسس والمدد والمهل، دورة DSR/incident/transfer صناعية، تصدير GRC مبصم، schedule لمراجعات الوصول، ودورة نشر policy تحفظ النص والمواد والإصدار.
8. **البيانات الأساسية:** قرار API/UI للدليل المرجعي، تحميل مصادر الدول/البنوك/البعثات القابلة للمراجعة، رفع coverage الخيارات، department-level shadow compare، ودورة publish/import لشجرة الكتالوج.

### P2 — نضج وقياس وقابلية توسع بعد إغلاق P0/P1

1. تنفيذ PDF عربي خادمي، تسليم تقارير خارجي محكوم، وتوسيع التصدير/الأرشفة المتوافقة بعد اعتماد الاحتفاظ.
2. تحويل BLOB SQLite المحدود إلى تخزين كائنات محكوم، مع سياسة احتفاظ واستعادة وحمل للملفات.
3. semantic search أو فهرسة تزايدية وbenchmark للبحث، مع عدم فهرسة البيانات المحظورة وبوابة privacy.
4. اختبارات متصفح E2E، حمل، اختراق، failure/recovery، ومصفوفة authorization/tenant لجميع endpoints؛ لا تعتمد syntax/check بديلًا.
5. مراقبة مؤسسية: logs مركزية محمية، metrics/SLO، health probes، alerts، runbooks، استمرارية worker/queue، وتمارين حوادث.
6. تحسينات تجربة المنتج: lazy loading لمساحات العمل، graceful partial failure، portal/قنوات عميل فقط إذا أُقرت، وقياس CX خارجي مرتبط بالعقد والحل.

## 9. منهج الدليل والاختبارات والقيود

- **أدلة قوية نسبيًا:** migrations وقيود SQL، وحدات الخادم، تسجيل المسارات، واجهات تستدعي API، ونتائج TAP مكتملة محددة تحت Node24 حيث وردت صراحة.
- **أدلة محدودة:** `node --check` و`npm run check` وفحص source hashes وقراءة الاختبارات. هذه تؤكد صياغة/نزاهة/وجود تغطية تصميمية فقط، ولا تؤكد السلوك أو العزل في تشغيل حقيقي.
- **أدلة غير كافية للجاهزية:** نتائج تاريخية، handoff، acceptance scripts غير موقعة، نتائج بدأت ثم لم تعط TAP summary، أو تشغيل أوقف لتزاحم بيئة مشتركة.
- **قيد بيئي رئيسي:** تعطل Node22/SQLite دون FTS5 قبل assertions في عدد كبير من الحزم. يجب تسجيله كحاجز تحقق لا كعيب وظيفي مثبت ولا كاجتياز.
- **لا أدلة تشغيل خارجية:** لا bank/payment/e-invoice/tax filing/e-sign/client portal/advertising platform/SSO/AI provider/monitoring أو DR حي في نطاق هذه المراجعة.

## 10. الخلاصة

منصة 3,6T خارج HCM هي **أساس برمجي محلي واسع ومحكوم بدرجات متفاوتة**، وليست منصة أعمال مؤسسية جاهزة للتشغيل أو الامتثال أو التكامل الخارجي. أقوى ما فيها هو بنية السجلات، القيود، العزل، فصل الواجبات، والإصدارات/التدقيق في وحدات كثيرة. أكبر فجواتها ليست تجميل واجهات فقط؛ بل موانع حوكمة وأمن وإثبات وتشغيل: عزل policy library، MFA/DR/observability، أصول السياسات الموقعة، بيئة اختبار قابلة للإعادة، قبول الملاك، وتكاملات أو حدود يدوية صريحة.

لا يجوز أن تتحول نواة الكود إلى ادعاء بأن بنكًا أو ضريبة أو فاتورة أو توقيعًا أو رسالة عميل أو AI provider أو التزامًا تنظيميًا قد نُفذ. المسار الصحيح هو: **إغلاق P0، توحيد دليل الاختبار، اعتماد الملاك والسياسات، UAT صناعي محكوم، ثم قرار منفصل لكل تكامل وتشغيل مؤسسي**. إلى أن يتحقق ذلك، الحكم الملزم هو **غير جاهز للإنتاج**.

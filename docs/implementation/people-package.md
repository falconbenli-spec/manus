## المسار المنفذ

ينشئ مدير حالي داخل نطاقه طلب احتياج لشاغر مصطنع واحد. لا يستطيع العميل اختيار مدير آخر أو الحالة. يلزم عنوان الوظيفة والمهارات ومبرر الاحتياج ومرجع خطة ومخصص مصطنعين وتاريخ احتياج ومعايير مقابلة. يحفظ الطلب نسخة ثابتة ويبدأ pending_need؛ يعتمده HR في الإدارة المحددة بالنطاق ليصبح open، أو يرفضه بسبب. لا يعتمد المدير احتياجه بنفسه. لا ينشأ مرشح قبل هذا الاعتماد.

يسجل HR ملف المرشح بعد اعتماد الاحتياج، بهوية UUID مستقلة وبريد اتصال موحد للحروف الصغيرة وفريد داخل الكيان. تقبل العينة عناوين تنتهي بـ.invalid فقط. يلزم مصدر الترشيح ودليل موافقة خصوصية مصطنعة وتاريخ نهاية عرض البيانات؛ يثبت الخادم مرجع الخصوصية من نسخة سياسة النطاق. يمنع تكرار الاتصال إنشاء سجل ثانٍ. طلبات متعددة للمرشح نفسه ليست مدعومة في هذه الحزمة؛ لا يعاد استخدام ملفه عبر احتياجات مختلفة تلقائيًا.

يمر المرشح بالمراحل التالية:

| الحالة | الفعل الذي ينقلها | الدليل والقرار |
| --- | --- | --- |
| applied | screen من HR | نتيجة فرز موثقة |
| screened | schedule_interview من HR | تاريخ مقابلة في الرياض وسبب التحديد؛ يثبت HR الحالي ومدير الاحتياج كمقيمين |
| interviewing | evaluate من كل مقيم | درجة0–5 ودليل لكل معيار معتمد، وتوصية وسببها؛ لا يقيم أحد قبل تاريخ المقابلة |
| evaluated | propose_offer من HR | مقترح أجر ومزايا وشروط وتواريخ وسبب، بعد اكتمال التقييمين |
| offer_pending | approve_offer من مدير الاحتياج | قرار مستقل عن معد المقترح ودليل مراجعة |
| offer_approved | accept_offer من HR | تاريخ قبول ومرجع إثبات للنسخة المعتمدة |
| accepted | start_onboarding من HR | عناصر بملاك ومواعيد ومعايير إكمال ودليل خطة |
| onboarding | complete_onboarding من HR | اكتمال جميع العناصر من ملاكها مع أدلتهم ثم مراجعة HR |
| completed | نهاية قائمة العينة | لا ينشأ حساب موظف أو راتب أو تعيين فعلي |

يستطيع HR إغلاق ترشيح قبل القبول بسبب مسجل، ويستطيع المدير رفض مقترح العرض. الرفض نهائي في هذه الحزمة. لا توجد إعادة فتح عامة أو تعديل صامت للمرشح. لا تمنح زيارة صفحة الترحيب حالة اكتمال للتهيئة.

معايير المقابلة من2 إلى8 معايير؛ لكل منها رمز واسم ووزن صحيح ودليل قبول مطلوب. مجموع الأوزان100. واجهة العينة تدخل معيارين؛ API يقبل حتى8. تبقى توصيات وأدلة المقيم الآخر مخفية حتى يسجل المستخدم تقييمه أو يكتمل التقييمان. لا تنسخ التوصية إلى سجل أحداث مكشوف أثناء الحجب. لا يؤدي مجموع الدرجات أو توصية الاستمرار وحدهما إلى قرار عرض أو قبول؛ يوجد إعداد HR وقرار مدير مستقلان مع الدليل.

الأجر المصطنع نص عشري يحول إلى وحدات العملة الصغرى دون فاصلة عائمة، مع عملة وبدلات وصفية وشروط وتاريخ التحاق مقترح وصلاحية. لا يرسل عرض عمل رسمي. عند تعديل أي عنصر من المقترح يحفظ إصدار جديد ثابت وتعود الحالة إلى offer_pending؛ يفشل القبول حتى اعتماد النسخة الجديدة. يثبت دليل القبول رقم نسخة العرض وتاريخ القبول. يمنع قبول مرشح ثانٍ للشاغر الواحد حتى مع طلبين متزامنين.

## التفويض والخصوصية

people_policies تربط department_id بإدارة HR المحددة hr_department_id ومرجع خصوصية ومدة سريان، مع synthetic=1. هذا إعداد مصطنع صريح وليس صلاحية عامة لـHR على كل الكيانات. تنشأ نسخة جديدة عند تغيير الإعداد؛ السجل ثابت. يتطلب بدء الاحتياج والمراحل الإيجابية سياسة سارية ومديرًا حاليًا نشطًا في نطاقه.

يعاد تحميل المستخدم النشط والدور والإدارة عند كل قراءة وفعل. يرى مدير الاحتياج ملفه فقط إذا بقي مديرًا في الإدارة نفسها، ويراه HR في نطاق السياسة. لا يرى المدير الآخر في الإدارة نفسها بيانات المرشح لمجرد منصبه. يرفض admin التقني، وتعزل الكيانات والموظفون غير المخولين. لا توجد صلاحية استثنائية شاملة.

أصحاب عناصر التهيئة يرون عناصرهم وعنوانها وموعدها ومعيارها فقط. لا تمنح المهمة صلاحية ملف المرشح أو الاتصال أو المقابلات أو العرض، ولا تتضمن استجابة المهمة لهم candidate_id. لا يكمل HR عنصرًا مسندًا لشخص آخر. التكليف لشخص خارج الكيان أو غير نشط أو admin مرفوض.

عند انتهاء retention_until يحجب ملف المرشح والتقييمات والمقترح من API، وتظهر للمخولين قائمة محدودة بمعرفات الملفات التي تحتاج مراجعة احتفاظ. تبقى البيانات محفوظة؛ لم ينفذ حذف فعلي أو تمديد مدة أو إجراء تسوية قانونية. لذلك يبقى معيار TAL-02 الخاص بسياسة الحذف والاحتفاظ جزئيًا. إشارات السياسة والتواريخ في هذه العينة ليست اعتمادًا قانونيًا أو سياسة شركة.

نسخ الاحتياج والمرشح والعرض والقبول وقائمة التهيئة ثابتة، والأحداث والتقييمات غير قابلة للمحو أو التعديل. الحدث الخاص بالمرشح يبقى داخل ملفه المخول؛ audit العام لا ينسخ الاتصال أو الدرجات أو نصوص أدلة المرشح. كل طفرة تتطلب transaction من المستدعي وتستخدم audit الموحد داخلها. اختبار تعطل التدقيق يثبت رجوع إنشاء المرشح ونسخة الاحتياج معًا.

## عقد API للمنسق

| الدالة | الاستخدام |
| --- | --- |
| listPeople(db,u) | user وpolicies وrequisitions وcandidates وtasks وassignees وretention_due ضمن التفويض؛ environment=synthetic وtimezone=Asia/Riyadh وtoday |
| createRequisition(db,u,input) | إنشاء احتياج: policy_id,title,need,plan_reference,budget_evidence,target_date,criteria |
| addCandidate(db,u,requisitionId,input) | version,name,contact,source,consent_evidence,retention_until؛ يعيد المرشح الجديد |
| getPeopleRecord(db,u,id) | طلب احتياج أو ملف مرشح بالصلاحية الحالية؛ يستعمل لقراءة createOnce |
| peopleAction(db,u,id,action,input) | قرار على الاحتياج أو المرشح؛ add_candidate يحيل إلى addCandidate |
| completeOnboardingTask(db,u,id,input) | version,evidence؛ إكمال عنصر من مالكه الحالي فقط |

المسارات المقترحة للربط: GET /people، POST /people/requisitions، POST /people/:id/:action، POST /people/tasks/:id/complete. كل إنشاء يحتاج createOnce على HTTP، بما فيه add_candidate؛ البصمة والمفتاح يقرآن الملف المأذون الحالي عند التكرار. كل قرار آخر يتطلب version، وواجهة peopleUI تثبت النسخة والمرجع عند فتح النموذج.

| action | الحقول الإضافية بعد version |
| --- | --- |
| approve_need, reject_need, cancel_need | note |
| screen, approve_offer, reject_offer, reject_candidate, complete_onboarding | evidence |
| schedule_interview | interview_date,evidence |
| evaluate | scores:[{key,score,evidence}],recommendation:proceed أوdo_not_proceed,evidence |
| propose_offer | monthly_base,currency,start_date,valid_until,benefits,conditions,evidence |
| accept_offer | accepted_on,evidence |
| start_onboarding | items:[{title,owner_id,due_date,acceptance}],evidence |

كل سبب ودليل مطلوب بثلاثة محارف على الأقل. تواريخ الأعمال YYYY-MM-DD، وسجل التوقيت UTC. يقارن القبول بيوم قرار الاعتماد في الرياض، بما فيه انتقال نهاية السنة عند00:30. لا تقبل حقول غير معرفة أو تغيير هوية المالك من المدخلات.

تهيئة نطاق العينة لا تنشئ حسابات:

```text
people_policies:
id, tenant_id, department_id, hr_department_id, name,
effective_from, effective_to, privacy_reference, synthetic=1, created_at
```

مثال الربط المحلي هو creative إلىhr في كيان36t، باسم ومرجع خصوصية مصطنعين وتواريخ سارية يختارها المنسق. لا يحتاج المنطق عدد مستخدمين أو معتمدين مخترعًا. يستخدم الاختبار المدير وHR الموجودين، ويكلف عنصرًا لحسابIT المصطنع دون تعديل صلاحياته.

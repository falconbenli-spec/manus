# حزمة المشتريات المحلية

نُفّذ احتياج شراء مرتبط بمشروع، مع عروض محفوظة وترسية واعتماد أمر داخلي واستلام جزئي أو كامل وتسجيل مرجع فاتورة المورد ومطابقة ثلاثية تنشئ سجل مستحق محليًا. جميع البيانات المستخدمة في الاختبارات مصطنعة. إصدار الأمر هنا سجل داخلي ثابت؛ لا ينشئ الملف فاتورة رسمية ولا يرسل أمرًا للمورد ولا ينفذ دفعًا أو ترحيلًا في نظام مالي.

مصادر العمل المقروءة: AGENTS.md وSTATUS.md وPLAN.md وdocs/decisions.md وsources/360_Codex_Master_Prompt.md، وبنود PRC-01 إلى PRC-10 وFIN-01 إلى FIN-10 من sources/requirements.catalog.json. بقيت النصوص ومعايير القبول الأصلية دون تغيير.

## ملفات الحزمة وعقد الاستدعاء

- app/procurement.mjs: المنطق والتفويض والتحقق من البيانات.
- app/migrations/005-procurement.sql: الجداول الجديدة والقيود وحماية السجلات والنسخ.
- tests/procurement.test.mjs: اختبارات الرحلة والرفض والعزل والتكرار.
- app/static/procurement-ui.mjs: مقارنة العروض وعرض مراحل الشراء ونماذج الأفعال المأذونة؛ يرتبط بمشغل الواجهة المشترك.
- docs/implementation/procurement-package.md: هذا العقد وحدود التغطية.

يستدعي الخادم `listProcurement(db,user)` لقراءة قائمة السجلات المأذونة. ويستدعي `createPurchase(db,user,input)` و`procurementAction(db,user,id,action,input)` داخل `transaction(db,...)` نفسها التي تحفظ مفتاح منع تكرار الإنشاء؛ يرفض الكود الكتابة دون معاملة نشطة بخطأ `transaction_required`. يُعاد الاستعلام عن الحساب والدور والنطاق من القاعدة في كل استدعاء، ولا تُستخدم قيمة الدور الواردة من العميل لمنح الوصول. تتولى طبقة HTTP المصادقة وCSRF وOrigin وحفظ مفتاح محاولة إنشاء ثابت عن طريق `createOnce`.

مدخل الإنشاء:

```json
{
  "project_id": "معرف مشروع مصطنع موجود",
  "title": "احتياج طباعة مصطنع",
  "specification": "خمس نسخ وفق مواصفات المشروع",
  "cost_center": "SYNTHETIC-CC-1",
  "due_date": "2026-10-20",
  "quantity": 5,
  "unit": "نسخة",
  "budget_amount": "100.00",
  "budget_evidence": "دليل المخصص المحلي لهذا الاحتياج",
  "currency": "SAR"
}
```

تحدد الجلسة `requester_id` و`tenant_id`. يرفض الخادم هوية مزورة أو حالة أو قيمة مالية داخلية في المدخل. `edit` يحتاج جميع حقول الإنشاء عدا `project_id` إضافة إلى `version`، وهو متاح لصاحب المسودة قبل التقديم فقط.

| الفعل | المدخل إضافة إلى version | الضابط والنتيجة |
| --- | --- | --- |
| submit | لا حقول إضافية | صاحب المسودة يقدم الاحتياج؛ تصبح الحالة sourcing وتتجمد بياناته |
| add_quote | supplier_key، supplier_name، unit_price، technical_assessment، financial_terms، delivery_date، evidence | صاحب الاحتياج يسجل عرضًا ثابتًا أثناء sourcing؛ المورد المحلي لا يكرر داخل الاحتياج |
| award | quote_id، note | مدير مخول مختلف عن صاحب الاحتياج يختار عرضًا من عرضين لمعرفي موردين مختلفين، مع مبرر وتأكيد المخصص؛ تصبح awarded |
| approve_order | terms، delivery_date، note | المعتمد المستقل ينشئ نسخة أمر ثابتة من العرض الفائز؛ تصبح ordered |
| receive | quantity، reference، evidence | مستخدم مأذون يسجل الاستلام؛ تمنع الزيادة والمرجع المكرر؛ تصبح part_received أو received |
| record_invoice | supplier_reference، quantity، amount، evidence | تسجيل مرجع صادر عن المورد المختار؛ يفحص السعر والكمية والمبلغ التراكمي وحدود الأمر والتكرار |
| match | invoice_id، note | معتمد مخول مختلف عن صاحب الاحتياج ومسجل الفاتورة يطابق كمية مستلمة غير مستهلكة بمطابقة سابقة وينشئ المستحق مرة واحدة |
| reject | note | معتمد مستقل يرفض sourcing أو awarded؛ حالة نهائية |
| cancel | note | صاحب الاحتياج يلغي draft أو sourcing؛ حالة نهائية |

كل فعل يحتاج نسخة حالية صحيحة. تكرار الفعل على النسخة القديمة يرد `stale_version` دون سجلات جزئية. المحاولة بمفتاح إنشاء سابق تقرأ السجل بصلاحياته الحالية؛ لا تعيد استجابة قديمة بعد سحب الوصول.

تعيد السجلات `allowed_actions` للاسترشاد في الواجهة. وجود `match` في هذه المصفوفة لا يتجاوز التحقق من استقلال مسجل الفاتورة والكمية المستلمة عند تنفيذ الفعل. تشمل البيانات `quotes` و`award` و`order` و`receipts` و`invoices` و`payables` و`history`. تحتوي `history` على لقطة كاملة لكل نسخة، مرتبطة بالفعل والفاعل والوقت. لا تعدل العمليات النسخ السابقة أو قرارات الترسية أو الأمر أو أدلة الاستلام والفاتورة أو المستحق.

## نطاق الوصول

صاحب الاحتياج بدور employee أو manager أو pm يجب أن يكون عضوًا حاليًا في المشروع. الموظف يرى احتياجاته فقط. المدير يرى احتياجات فريقه المباشر في إدارته الحالية بشرط عضويته في المشروع. تراجع القاعدة علاقة `manager_id` والإدارة في كل قراءة وفعل. مسؤول التقنية admin والأدوار غير المهيأة لا تقرأ هذه السجلات لمجرد المسمى.

مدير المشروع pm يحتاج تصريح تكلفة مستقل لقراءة احتياج شخص آخر في المشروع، محفوظًا في `procurement_project_grants`. ملكية المشروع وحدها لا تمنحه بيانات التكلفة. العضوية الحالية شرط دائم؛ حذفها يحذف المنحة التابعة ويمنع الوصول فورًا. صاحب الاحتياج لا يعتمد طلبه حتى لو تغير دوره إلى manager.

يمكن لتهيئة الاختبار إضافة منحة مصطنعة بعد إنشاء مشروع بعضوية pm:

```js
db.prepare('INSERT INTO procurement_project_grants VALUES(?,?,?,?,?)').run(
  projectId, pmId, managerId,
  'تصريح تكلفة مصطنع لهذا المشروع فقط',
  new Date().toISOString()
);
```

يجب أن يكون المانح `managerId` منشئ المشروع وعضوًا نشطًا بدور manager، والمستفيد عضوًا نشطًا بدور pm في الكيان نفسه، وبهوية مختلفة. لا توجد واجهة عامة لإدارة المنح في هذه الحزمة؛ مثال التهيئة مخصص لقاعدة اختبار مصطنعة. إدارة التفويض المؤرخ ومراجعته وإشعاراته عمل لاحق.

## حساب الكمية والقيمة والمطابقة

كل احتياج يمثل بندًا واحدًا بوحدة مسجلة، والكمية عدد صحيح من 1 إلى 1000000. العملة الوحيدة المهيأة للاختبار هي SAR. تدخل الأموال كنص عشري موجب بمنزلتين كحد أقصى؛ تتحول بواسطة BigInt إلى هللات صحيحة، ثم تحفظ داخل INTEGER. يرفض الكود الأعداد العشرية المرسلة كـ JSON number والصيغة العلمية والقيم السالبة والمنزلة الثالثة. لا يحدث تقريب صامت: `10.01 × 5` يساوي 5005 هللات.

سقف المبلغ المحفوظ 1000000000000 هللة هو حد تقني محلي لحماية الحساب؛ ليس حد تفويض أعمال أو سياسة شراء للشركة. يبدأ المخصص كبيان احتياج مع دليله، ويؤكده معتمد الترسية المستقل. لا تنفذ هذه الحزمة حجزًا من موازنة مشروع مشتركة، ولا تفحص استهلاك احتياجات أخرى للمخصص نفسه؛ لذلك تبقى PRC-01 وFIN-02 جزئيتين.

قيمة الأمر تساوي الكمية المطلوبة مضروبة في سعر وحدة العرض الفائز. يرفض الاستلام الذي يتجاوز كمية الأمر، ويرفض تسجيل مرجع فاتورة إذا اختلف مبلغه عن كميته مضروبة في سعر الوحدة، أو تجاوز مجموع الفواتير كمية الأمر أو قيمته. تسجل الفاتورة قبل الاستلام الكامل إذا طابقت الأمر، لكن المطابقة لا تنشئ مستحقًا حتى تتوفر كمية مستلمة كافية بعد خصم الكمية التي استهلكتها المطابقات السابقة. يمكن أن تغطي فاتورتان كميات جزئية مستقلة من الأمر نفسه.

السماح المحلي للفروق صفر، وهو قيد هندسي تحفظي لهذه العينة، وليس سماحًا ماليًا اعتمدته الشركة. تحتاج معالجة الاختلافات والإشعارات الدائنة وإلغاء المراجع وتصحيحها ومسار إعادة اعتماد الأمر إلى حزمة لاحقة. لا يمكن تعديل مرجع سجل بالفعل بصمت لتجاوز هذا القيد.

مرجع الفاتورة فريد داخل الكيان للمورد المحلي نفسه عبر جميع أوامر الشراء. يوحد التطبيع NFKC حالة الحروف والمسافات قبل المقارنة. `supplier_key` معرف محلي يدخله المستخدم، ولم ينفذ سجل تأهيل قانوني أو تحقق من أن اسمين أو معرفين مختلفين يعودان إلى المورد القانوني نفسه؛ يبقى ذلك ضمن PRC-02 وPRC-10.

لا تضيف الحزمة نسبة ضريبة أو قاعدة فوترة من الذاكرة. `tax_policy=not_configured` و`document_kind=supplier_reference` يصفان البيانات. يجب أن تتطابق القيم المدخلة على الأساس نفسه؛ فاتورة تحتاج مكونات ضريبية مستقلة تتطلب تهيئة معتمدة قبل تسجيلها هنا.

`procurement_payables` سجل استحقاق داخلي فقط. ليس قيدًا مزدوجًا، ولا يمثل حسابات أستاذ أو مدينًا ودائنًا أو إقفال فترة. تبقى FIN-06 خارج تنفيذ هذه الحزمة؛ `posting_status=not_posted` و`payment_status=not_paid` ثابتتان بقيود القاعدة. لم ينشأ outbox أو قبول فاتورة رسمي أو تنفيذ مصرفي من هذه العمليات.

## التغطية وحدود القبول

| الرموز | الدليل المنفذ | ما بقي |
| --- | --- | --- |
| PRC-01 | مشروع وعضوية ومواصفات ومركز تكلفة وموعد ومخصص بدليل وفحص قيمة الترسية | الموازنة المرجعية والحجز المشترك والاستثناء المعتمد |
| PRC-03 | مدخلات فنية ومالية ودليل لكل عرض ومقارنة عرضين وترسية موثقة مستقلة | دعوات الموردين وسجل التأهيل ومعايير الشركة المعتمدة |
| PRC-04 | ترسية تسبق أمرًا داخليًا معتمدًا ثابتًا | إصدار أو تصدير خارجي مأذون وربط المورد |
| PRC-05 | استلام جزئي وكامل بكمية ومرجع ودليل وفاعل | سير طالب الدفع وفصل الاستلام عنه عند تطبيق الدفع |
| PRC-06 | مطابقة أمر واستلام ومرجع فاتورة؛ الزيادة أو الفرق لا ينشئ مستحقًا | سياسة السماحات والاستثناءات وتعيين مسؤول معالجة الفرق |
| PRC-08 | منع تعديل الأمر المعتمد وحفظ نسخه | مسار تعديل أمر وإعادة اعتماد أثره |
| FIN-05 | مرجع فاتورة مرتبط بالأمر والمورد ووقف الرقم المكرر | الإشعار الدائن والتسويات وسجل المورد المرجعي |
| FIN-07/08 | حالات صريحة تفصل الاستحقاق عن الدفع والمرجع عن إصدار رسمي | التكامل المصرفي والمالي والفوترة والضريبة |

PRC-02 وPRC-07 وPRC-09 وPRC-10 غير منفذة في هذه الحزمة. لا تعادل هذه التغطية إكمال WF04 أو اعتماد أي متطلب كامل من مالك الإجراء.

## الاختبارات الفعلية

في 10 سبتمبر 2026 نجح `node --test tests/procurement.test.mjs`: 13 اختبارًا، صفر فشل أو تخطي، بعد المراجعة الأخيرة بزمن 589.335417ms. تغطي الاختبارات مسار خمس وحدات بسعر 10.01 ريال للوحدة إلى استلامين ومستحقين بإجمالي 50.05 ريال؛ وفشل الاعتماد الذاتي والقفز والفرق والكمية الزائدة والتكرار؛ وعزل المشروع والكيان والدور والإدارة وسحب العضوية؛ ومنع تعديل النسخ وإثبات rollback عند فشل كتابة التدقيق. تختبر الواجهة تثبيت النسخة في النموذج وتحويل الكمية وهروب بيانات HTML وغياب style inline المحظور في CSP. ظهرت أثناء الكتابة مشكلة اختيار العرض بالترتيب في fixture عندما تشترك عروض في الطابع الزمني؛ أصلحت بيانات الاختبار لتختار معرف المورد المقصود صراحة، ثم أعيدت الاختبارات.

نجح `npm run check` عند الفحص المشترك الأخير: 34 وحدة JavaScript، وبصمات المصادر، وتطابق 220 متطلبًا و22 مجالًا. هذا ليس فحص TypeScript أو تدقيقًا أمنيًا شاملًا.

توقف `npm test` الأول داخل sandbox عند اختبارات HTTP بخطأ `listen EPERM`، وظهر افتراض قديم لعدد الترحيلات. بعد إصلاح اختبار العد وإعادة التشغيل بصلاحية المستمع المحلي نجح 72 من 73 اختبارًا في 1147.709125ms؛ بقي فشل fixture في `tests/ui-race.test.mjs` عند `pending.get(...)`. جميع اختبارات المشتريات وHTTP والترحيلات نجحت في تلك الجولة. أُبلغ منسق الدمج بالنتيجة لملكية ملف الواجهة المشترك، ولم تُضعف اختبارات العزل أو السباق. نتائج الدمج اللاحقة تُسجل في توثيق الاختبار العام وSTATUS.md.

أُجريت اختبارات هذه الحزمة على SQLite داخل الذاكرة. لم تعدل الحزمة قاعدة work/local.sqlite أو الحسابات أو البيانات الحقيقية، ولم تنفذ فحص متصفح. ملف واجهة المشتريات جاهز؛ تشغيله مع مشغل النماذج وAPI وفحصه في المتصفح مسؤولية الدمج في الجلسة نفسها.

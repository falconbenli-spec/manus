# نقل منصة HCM إلى منصة 3,6T

## القرار المعماري

تم اعتماد **منصة 3,6T كمنصة التشغيل المستهدفة**. لن يتم نسخ تطبيق React/Express أو قاعدة MySQL الخاصة بـ HCM حرفيًا، لأن منصة 3,6T تعمل بتصميم مختلف ومقصود:

- Node.js 24 مع `node:sqlite`.
- خادم `node:http` بلا اعتماديات تشغيل خارجية.
- واجهة JavaScript عربية RTL مع CSP صارم.
- ترحيلات SQLite مرتبة لا تُعدّل بعد إضافتها.
- صلاحيات متعددة الشركات وسجل تدقيق ومعاملات محلية.

وبالتالي يكون النقل **وظيفيًا ومحكومًا**: كل وظيفة تُربط بوحدة أصلية في 3,6T أو تُبنى كوحدة أصلية فوق مخططها، مع بقاء HCM نسخة رجوع وعدم نقل أي بيانات تشغيلية أو أسرار أو تكاملات خارجية.

## ما تم العثور عليه

تحتوي 3,6T مسبقًا على خريطة `app/hcm-reference.mjs` وتغطية تشغيلية عبر `app/hr-operations.mjs` والوحدات المتخصصة. كما أن ترحيل `200-hr-operations.sql` يضم الفجوات التي كانت محددة سابقًا:

- قاموس الكفاءات ومصفوفة المهارات.
- خطط تحسين الأداء PIP.
- الاستبانات العامة مع نمط مجهول/مسمى وحجب النتائج الصغيرة.

هذه ليست بيانات من HCM؛ إنها إعادة تنفيذ أصلية محكومة داخل 3,6T.

## قواعد البيانات

لم يتم دمج قاعدة HCM أو نسخ سجلات الموظفين والرواتب والإجازات. قاعدة 3,6T تُبنى فقط من ترحيلاتها المحلية، وأي ترحيل بيانات حقيقي يحتاج حزمة منفصلة تشمل:

1. نسخة مصدر رسمية.
2. مخطط تحويل ومطابقة معرفات.
3. فحص تكرارات وعزل الشركات.
4. استيراد تجريبي بلا كتابة على الإنتاج.
5. قبول مالك بيانات الموارد البشرية.
6. اختبار استعادة وتدقيق بعد الاستيراد.

## الفحوص المطلوبة قبل الإغلاق

- `npm run check` لمنصة 3,6T.
- اختبارات وحدات HCM المدمجة: الكفاءات، PIP، الاستبانات، الوصول والعزل.
- `npm test` الكامل مع توثيق الفشل السابق وعدم تحديث Golden دون مراجعة.
- فحص واجهة RTL والجوال والسطح المكتبي.
- مراجعة عدم وجود أسرار أو بيانات HCM حقيقية في Git.

> لا يُعتبر النقل مكتملًا تشغيليًا لمجرد وجود الخريطة؛ الإغلاق يتطلب نجاح الاختبارات وقبول مالك إجراءات الموارد البشرية.

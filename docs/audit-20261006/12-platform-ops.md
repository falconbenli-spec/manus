## 3. أدلة الاختبارات القابلة للتحقق

### 3.1 تشغيل هذا التدقيق

1. **فحص المصدر — ناجح:**
   ```text
   /home/ubuntu/.nvm/versions/node/v24.21.0/bin/node scripts/check.mjs
   Syntax checked: 864 JavaScript modules. Source hashes match.
   Traceability: 220 requirements / 22 domains.
   Migrations: 183 planned, highest 206.
   ```
   أداة الفحص نفسها تنبه أنها ليست محلل أمن شامل ولا build production.

2. **اختبار النسخ والاستعادة المحدد — ناجح:**
   ```text
   node v24.21.0
   tests/files-security.test.mjs
   criterion 15: a backup is proven by restoring it elsewhere ...
   tests 1 · pass 1 · fail 0 · skipped 0
   ```
   الحالة تختبر `backupDatabase` ثم `restoreCheck` على قاعدة اختبار، وتتحقق من السلامة والمفاتيح وسلسلتي التدقيق والفواتير، وتحاول كشف العبث بسجل التدقيق (`tests/files-security.test.mjs:71-82`).

3. **حزمة مركزة للأمن/الصلاحيات/التشغيل — نتيجة مضمّنة من runner:** شغلت Node `v24.21.0` مع 12 ملفًا: `access`, `access-two-person`, `authorization-race`, `login-audit`, `totp`, `tenant-identity`, `observability`, `platform-health`, `integration-readiness`, `remote-access`, `outbound-audit`, `security-regressions`. ظهر في مخرجات runner:
   ```text

   ```
   العملية نفسها أعادت رمز خروج 1 رغم ملخص runner الأخضر، ولم يستمر ملف الالتقاط المؤقت؛ لذلك تسجل النتيجة كدليل تشغيل جزئي قابل للمراجعة من المخرجات، **لا كبديل عن إعادة تشغيل الحزمة تحت بوابة إصدار نظيفة**.

4. محاولة أولى باستخدام Node `v22.13.0` فشلت قبل الاختبارات لأن SQLite المدمج يفتقد `fts5` (`no such module: fts5`). لم تستخدم النتيجة للحكم على الشفرة؛ المشروع يطلب `>=24.14 <25` في `package.json`، ثم أعيد التحقق بـNode 24.21.0.

## 4. الفجوات والمخاطر

### حرجة قبل أي تشغيل حقيقي

1. **التكاملات غير جاهزة:** `integrationReadiness` يقول صراحة `none_active`، وكل الموصلات `adapter_implemented:false` و`last_success:null`. لا يوجد ربط حكومي أو مصرفي أو هوية مؤسسية أو تخزين مؤسسي أو نقل بيانات مثبت. البريد قابل للتهيئة فقط، وليس دليل تسليم حي.
2. **العزل/نطاق الإدارة غير مكتمل منهجيًا:** `app/access.mjs:173-208` يقرر أن `CONFINED_IN_CODE` يحوي فقط `department.levels.manage`، وأن تصاريح department الأخرى تقبل نطاقًا لكن كثيرًا منها لا يصفّي صفوفًا لاحقًا. وتقول `docs/readiness/OWNER-ACCEPTANCE-MATRIX.md:58-60` صراحة إن عيب `holds()` مفتوح: منحة ضيقة قد تجيز اعتمادًا خارج النطاق، وإن العرض لا يقدم قبل إصلاحه. هذه ليست فجوة وثائقية فقط؛ هي حد معلن في إنفاذ الصلاحية.
3. **MFA حساس اختياري افتراضيًا:** `security_settings.require_mfa_for_sensitive` لا يفرض إلا بقرار الأدمن الأول. `docs/operations/REMOTE-ACCESS.md:184-192` يقر أن فتح بيانات الرواتب/الجزاءات للإنترنت بكلمة مرور وحدها أضعف حلقة ما لم يفرض MFA أو طبقة وصول خارجية.
4. **تعافٍ مؤسسي غير مثبت:** آلية النسخ جيدة، لكن لا توجد في هذا التدقيق نسخة تشغيل متاحة أو إثبات أن `launchd` مثبت ويعمل أو أن النسخ خارج الجهاز. `docs/runbooks/local.md:28` ينص أن RTO/RPO غير معتمدين وأن الحفظ على نفس الجهاز ليس تعافيًا مؤسسيًا. `REMOTE-ACCESS.md:163-180` يطلب نقل نسخة مشفرة خارج الجهاز والتحقق الشهري.
5. **نقطة فشل وحيدة:** التشغيل المقترح جهاز Mac واحد وخدمة مستخدم محلية؛ لا HA ولا standby ولا خطة failover. `docs/operations/REMOTE-ACCESS.md:196-204` يقر أن عطل/سرقة القرص يوقف الشركة وأن النسخة تحمي البيانات لا الاستمرارية.

### عالية

6. **الرصد والتنبيه غير ناضجين:** الرصد هو JSON إلى stdout محلي ولقطة صحة محمية داخل التطبيق. لا يوجد دليل على مراقبة خارجية، paging، تنبيه لفشل الخدمة أو فشل النسخ، أو احتفاظ/تدوير سجلات. `docs/readiness/RELEASE-GATES.md` يسجل «سجلات مركزية ومراقبة وتنبيهات» مفتوحًا و`health check` جزئيًا.
7. **دليل الاستعادة الحديث متضارب/قديم بالنسبة للرأس الحالي:** توجد أدلة تاريخية: `docs/testing/restore-check-20260929-migration149.json` (migration 149) و`docs/testing/p3-finance-procurement-20261001/deploy.txt` (migration 178). لكن `scripts/check.mjs` يثبت أن الرأس الآن migration **206**. لم يتم في هذا التدقيق فتح نسخة تشغيل أو تشغيل استعادة عليها، لذا لا توجد شهادة مستقلة حديثة على ترحيل 206.
8. **مفتاح تشفير الحقول نقطة تعافٍ منفصلة:** فقدان `FIELD_KEY_PATH` يجعل أسرار TOTP والحقول المختومة غير قابلة للقراءة. هناك تحذير في `environment.mjs:74-88` من تعدد المفاتيح/غياب المفتاح، لكن لا توجد إدارة مفاتيح مؤسسية أو إجراء دوران/استرداد مثبت في النطاق.
9. **الوصول عن بعد يفك HTTPS عند Cloudflare إن اختير هذا الدليل:** `REMOTE-ACCESS.md:28-40` يوثق أن Cloudflare يرى كلمات المرور والرواتب والمرفقات عند الحافة. لا دليل في المستودع على Cloudflare Access أو قرار مالك موثق لقبول هذا الأثر.

### متوسطة

10. **CI ليست بوابة إصدار مثبتة:** `.github/workflows/verify.yml` يشغل `npm run check` و`npm test` فقط على pull request/manual، وREADME يقول إنه مضاف ولم يرفع أو ينفذ على GitHub. لا نشر مضبوط، لا required branch protection مثبت، ولا فحص اعتماديات/DAST/SAST/secret scanning ظاهر في النطاق.
11. **وضع production غير معرّف بدل أن يكون بيئة إطلاق مكتملة:** `environment.mjs` لا يعرف إلا `local` و`staging`، وREADME يذكر أن الخادم يرفض production ولا يوضع خلف وكيل بهذه الإعدادات. هذا مناسب كحاجز ضد إطلاق عرضي، لكنه ليس خطة إنتاج.
12. **الاختبارات قوية لكنها لا تساوي مراجعة مستقلة:** لا يوجد pentest أو مراجعة أمن خارجية مثبتة؛ الدليل نفسه يقر بهذا في `REMOTE-ACCESS.md:202-204`.

## 5. المطلوب قبل التشغيل

### بوابة منع تشغيل بيانات حقيقية أو وصول إنترنت

1. **أغلق فجوة حصر الإدارات أولًا:** عالج كل استعمال لـ`holds()`/`can()` في قرارات القراءة/الاعتماد بحيث يمرر ويحترم `department_id` أو يضيف RLS/قيودًا بقاعدة البيانات؛ اختبر محاولة grant ضيقة ثم اعتماد/قراءة خارج الإدارة في كل capability محصور. لا يكفي قبول نطاق في شاشة المنح.
2. **فعّل MFA إلزاميًا للتصاريح الحساسة** بعد حملة تفعيل وقياس `without_mfa=0`، ثم اختبر حجب كل تصريح حساس لحساب بلا TOTP. ضع طبقة وصول مؤسسية قبل صفحة الدخول إن فُتح الوصول عن بعد.
3. **نفذ تكاملًا واحدًا في sandbox فقط لكل جهة ذات أولوية:** عقد موثق، مالك بيانات، OAuth/credentials خارج المستودع، allowlist، idempotency، retry/dead-letter، اختبارات صلاحية وفشل/انقطاع، وسجل نجاح مستقل قبل تغيير الحالة إلى `active`.
4. **أنشئ سياسة نسخ وتعافٍ قابلة للقياس:** نسخة مشفرة خارج الجهاز ومنفصلة عن مفتاح الحقول، retention معلن، RPO/RTO معتمد، restore drill كامل إلى migration 206 أو ما يعادله، مطابقة counts/مرفقات/صلاحيات/سلسلة تدقيق، ومحضر موقّع.
5. **أضف مراقبة وتنبيهًا مستقلين:** تحقق خارجي من availability، إنذار لفشل الخدمة وفشل backup/restore وعمر النسخة وسلسلة التدقيق، احتفاظ logs وتدويرها، runbook incident وتمرين استجابة.

### قبل الإطلاق/الاستمرارية

6. **اعتمد بيئة إطلاق حقيقية أو قرارًا صريحًا بعدم الإطلاق:** لا تخلط local وstaging؛ ثبّت مسارات DB وfield key، host allowlist، `TRUST_PROXY` إن استعمل نفق، وHTTPS end-to-end أو قبول مخاطر الحافة. لا تفتح `LOCAL_BIND_HOST` على LAN.
7. **حوّل التحقق إلى release gate يعمل فعليًا:** شغّل Node 24.21.x، `npm run check`، full suite، fresh migration، restore latest backup، ومراجعة security scan في CI محمي/مطلوب؛ احتفظ بملف TAP ونتيجة البوابة وبصمة المصدر مع الإصدار.
8. **نفّذ مراجعة خارجية مستقلة** تشمل اختبار مصادقة/CSRF/host/origin، عزل المستأجر، IDOR، التصعيد بالصلاحيات، التصدير والمرفقات، وتكوين النفق/host.
9. **عيّن مسؤول تشغيل وبديلًا** وخطة استبدال الجهاز/استرداد key، وقبول المالك لمخاطر نقطة الفشل الواحدة وتكاملات Cloudflare إن اختيرت.

## 6. حدود التحقق

- لم تُستخدم بيانات أو أسرار حقيقية، ولم تُفتح `work/` أو أي قاعدة تشغيل.
- لم يُشغّل `npm start` أو أي نفق أو `launchd` أو بريد أو تكامل خارجي.
- اختبارات Node استلزمت Node 24.21.0؛ Node 22 في sandbox لا يوفر SQLite FTS5. هذا عائق بيئة وليس فشلًا وظيفيًا مثبتًا.
- لا تدعي نتائج الاختبارات المحلية أن خدمة macOS أو backup schedule أو Cloudflare أو CI تعمل حاليًا؛ هذه جميعها تحتاج دليل تشغيل حي منفصل.

## 7. خلاصة الحكم

**الحالة جزئية، لا مكتملة.** تتجاوز المنصة مجرد واجهة: فيها ضوابط مصادقة وجلسات وتدقيق وTOTP وRBAC ونسخ متحقق منه، والواجهة مرتبطة بمسارات حقيقية والاختبارات تغطي عددًا جيدًا من الرفض والنجاح. لكنها تبقى منصة محلية ذات بيانات مصطنعة ومجال عمليات غير مغلق: لا integration نشط، لا تعافٍ مؤسسي مثبت عند الرأس الحالي، لا رصد/إنذار مستقل ولا HA، وقيود نطاق الإدارات معلنة كغير مكتملة. لذلك لا أوصي بتشغيلها ببيانات شركة أو فتحها للإنترنت قبل تنفيذ بوابة القسم 5 وإعادة تدقيقها.

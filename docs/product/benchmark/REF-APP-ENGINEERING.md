# Reference app review: engineering, security and practice (old "HCM platform" vs 3,6T platform)

Date: 2026-09-19. Reviewer role: principal engineer / application-security review. Scope: the partial snapshot in `work/reference/manus-app/` (gitignored), compared with this repository.

**How to read this.** Every finding cites `file:line` in the snapshot. "Verified" means I read the code. "Probable" means the code strongly implies it but a file I could not see (listed in §0) could change the answer. I ran nothing from the old app and contacted no live system. I did not open `.zoho_tokens.json`, `cookies.txt`, `.manus/db` or any employee data file. No secret value, password, default-password pattern, name, phone number or e-mail address from the snapshot is reproduced here. Where the code holds one, this document gives the line number only.

Other notes on the same app: `REF-APP-FRONTEND.md` (front end). The owner has ruled that this platform is the system of record, so nothing here proposes migrating data from the old app or from Zoho. The old app is treated only as a security liability to close down and as a source of ideas.

## 1. Architecture and code-quality assessment

| **Structure** | Express 4 monolith. Handlers call `await import()` at run time. `any` is used throughout. | ~120 focused modules in `app/`, each owning its SQL and rules. Our practice of a proof script before and after each fix plus a named test (`docs/product/audits/SECURITY-FIXES.md`) is the right counter-model.

## 3. What they did well, and what to adopt in zero-dependency style

| Idea in the old app | How ours compares | Recommendation | Needs owner decision? |
|---|---|---|---|
| **XSS sanitising** (`xss` middleware on every body, `index.ts:216`) | We use output encoding (`e()` in `app/static/app.mjs`) and a CSP with `script-src 'self'`, no inline script (`app/server.mjs:148`). That is the stronger model. Input mutation corrupts legitimate text and gives false confidence (V11). | **Do not adopt.** Optional P3: a `check.mjs` rule that flags any `innerHTML=` template in `app/static/` that interpolates `${…}` without `e(`. | No |
| **Helmet-style headers** | Ours already sends CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, CORP `same-origin`, `Permissions-Policy` and `no-store` (`app/server.mjs:146-149`), plus sandbox CSP on downloads. **Missing:** `Cross-Origin-Opener-Policy: same-origin`, `Strict-Transport-Security` (only when served over HTTPS, i.e. when `previewOrigin` is set), `X-Permitted-Cross-Domain-Policies: none`, `Origin-Agent-Cluster: ?1`. | Add these four to the headers object, HSTS conditional on HTTPS (P2). | No |
| **`security.txt`** (`client/public/security.txt`) | None | Serve `/.well-known/security.txt` from `app/static` (P3). | Yes: the contact address |
| **Cron scheduling** (`node-cron` dependency, but `startDailyScheduler` is `setInterval(24h)` from boot, `index.ts:175-196`, which drifts and re-fires on restart) | We have 15- and 60-second tickers (`server.mjs:1285-1292`), a claimed job queue with retry and dead state (`app/jobs.mjs`), and period-idempotent report schedules (`report-schedules.mjs:47-57`). **Missing:** calendar-anchored daily jobs (e.g. 08:00 Riyadh reminders for expiring IDs, contracts and probation). | Add `dailyAt('08:00')` on the existing drain tick. Compute from `riyadhToday()` and dedupe on the key `(job_type, date)` through `jobs` claims. No library (P2). | No |
| **Excel and PDF reports** (`exceljs`, `xlsx`, `jspdf`, `html2canvas`: four dependencies, one with advisories) | `app/xlsx.mjs` is a zero-dependency multi-sheet writer with formula neutralisation. `app/print-documents.mjs` renders print HTML that the browser saves as PDF. | Adopt the **report content**, not the libraries: a weekly attendance-shortfall report (logic at `index.ts:509-609`: under-8-hour days, shortfall minutes, compliance rate) and a monthly per-employee attendance workbook. Build both on `xlsx.mjs` (P3). Server-side PDF only if e-mailed PDFs become a requirement. | The HR manager accepts the layouts |
| **E-mail delivery pipeline** (Resend over `fetch`, RTL HTML layout, `email_logs` with provider id, status and error, template table, throttled bulk send) | We have an `outbox` table (`workflow.mjs:474`, counted as "blocked" in `integration-readiness.mjs:23`). `jobs.mjs` deliberately forbids external side effects. **No e-mail leaves the platform today.** | Build an `outbox → dispatcher` loop outside DB transactions: claim a row, then `fetch` the provider's HTTP API with an idempotency key, then store the provider id, retrying with backoff and moving failures to a dead letter. Messages carry **notice + link only**, never salary, health or ID data. Escape every interpolated value. A test uses a fake provider via a base-URL env var, and a kill switch is required. HTTP APIs need no dependency. SMTP would need a hand-written `node:tls` client, so avoid it (P2). | **Yes**: provider, sending domain (SPF, DKIM, DMARC), who holds the API key, and a PDPL cross-border assessment if the provider stores mail outside the Kingdom |
| **Notifications** (categories, HR security alerts for shared devices and mock location, `index.ts:813-839`) | In-app notifications exist (`workflow.mjs:201,511`) for request events only. `notifications()` has no `LIMIT`. | Add a `category` column and **security alerts to platform admins**: repeated failed logins, MFA reset, capability grant, backup or restore-check failure. Add paging (P2). Do not adopt device-fingerprint or GPS alerts. | No (security alerts). Yes for any location tracking. |
| **Idle logout** (`hooks/useIdleLogout.ts`) | Sessions have an 8-hour absolute expiry and **no idle timeout** (`auth.mjs:48`). | Add a `last_seen` column and a server-side idle limit, e.g. 30 minutes for sessions holding finance, payroll or admin capabilities and 2 hours otherwise (P2). | Yes: the numbers |
| **Policy Q&A assistant** grounded in the work regulations | `app/ai.mjs`, `knowledge.mjs` and `ai-governance.mjs` exist. | Only after an LLM provider decision and a PDPL assessment. Keep the regulations as a knowledge record, not as a string in code. | Yes |

## 4. Risk note for the owner

**Plain summary.** The old app's Drive folder holds what look like working Zoho sign-in tokens and browser session cookies, 70+ database query logs, and files with employees' personal and salary data. The copied code also contains the old administrator and manager passwords in plain text. In the production code of the old app, **an employee's number is also their password** (V1). If that deployment is still online, anyone who knows an employee number can see that person's salary.

Recommended actions, in order. All of them are yours or IT's to perform. I have not touched any live system or any of these files.

1. **Revoke and rotate the Zoho access.** In the Zoho API console, delete or regenerate the OAuth client used by the old app and revoke its refresh tokens. Afterwards the old token must fail with an invalid-token error. Do this even though the company no longer uses Zoho as a system: an unrevoked token still opens the data held there.
2. **Treat `cookies.txt` as compromised.** Sign out of all sessions on whichever services those cookies belong to, and change those accounts' passwords. I did not open the file, so I do not know which services these are.
3. **Rotate every secret the old app used**: the database connection string and its user password, the Resend API key, the LLM gateway key, and the admin and manager passwords (both the env values and the hard-coded dev values in V2). Tell staff not to reuse any password they set in the old portal.
4. **Clean the Drive folder.** Remove `.zoho_tokens.json`, `cookies.txt`, `.manus/db/`, `.manus-logs/` if present, `client/src/data/*` employee files, and loose scripts or spreadsheets containing staff data. Check Drive **Manage access**: named people only, link sharing off. Review Drive activity for downloads. Permanent deletion from trash is a deliberate step for you to take after any retention decision. Our repository keeps its reference copy under `work/`, which is gitignored and never committed.
5. **Retire the old deployment if it is still running.** Find the hosting (the app's public URL constant is at `emailSystem.ts:20`) and take it offline. Then rotate the DB credentials. Decide with the HR manager whether any records must be archived under the HR retention policy before the database is destroyed. The end state: the URL serves nothing, the dev preview is stopped, and provider keys show as revoked.
6. **Decide on breach handling.** If any of the above was reachable by people who should not have it, assess with legal advice whether PDPL breach notification applies. The implementing regulation sets a short window (72 hours) to notify the regulator once a breach is known. This is a legal decision, not an engineering one.

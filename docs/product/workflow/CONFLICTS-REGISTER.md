# سجل التعارضات — دورة العميل والمشروع

تاريخ الإعداد: 20 سبتمبر 2026 · الإصدار: 1

---

## 0. كيف تُقرأ هذه الوثيقة

**كل توصية هنا رأي محلل أعمال، وليست سياسة شركة، ولا تصير سياسة إلا بقرار من الجهة المذكورة في عمود «من يقرر».**

التعارضات العشرة الأولى (CF-01…CF-10) هي التي أوردها المالك في برومبته. **وصلني وصفها المختصر لا نصها الحرفي**، فصياغة «القراءتين» أدناه إعادة بناء من ذلك الوصف ومن فحص الكود، وتحتاج مراجعة المالك قبل الاعتماد. التعارضات CF-11 فصاعدًا وجدتُها بنفسي أثناء قراءة المستودع، وأذكر لكل واحد دليله في الكود.

**قاعدة لم أخرقها:** حيث لا يوجد رقم في مصدر، لا أقترح رقمًا. أقترح **من يضع الرقم ومتى**، لا الرقم نفسه.

## 1. التعارضات العشرة التي أوردها المالك

### CF-01 — ملكية عرض السعر

| | |
|---|---|
| **القراءة الأولى** | العرض ملك **إدارة الأعمال** (business-dev): هي من تؤهّل وتسعّر وتصدر وتتابع حتى التوقيع، وتسلّم بعد الفوز. |
| **القراءة الثانية** | العرض ملك **إدارة الحسابات** (accounts) بوصفها مالكة العلاقة: الأعمال تجهّز، والحسابات تملك ما يصل العميل. |
| **أثر الأولى** | مسار واحد نظيف؛ الأعمال مسؤولة عن الرقم وعن الوعد. لكن مدير الحساب يرث وعودًا لم يوقّعها، وMOD-BD-04 يصير نقطة التسليم الوحيدة، فإن ضعف ضاع السياق. |
| **أثر الثانية** | العلاقة متصلة من أول لقاء. لكن الحسابات تصير مسؤولة عن تسعير لم تبنِه، وينشأ تفويضان على مستند واحد، وهو مصدر مباشر لتعارض CF-04 (ازدواج الرموز). |
| **ماذا يقول الكود اليوم** | `commercial.mjs` يعرف مالكًا واحدًا (`owner_id`) ومعتمدًا مديرًا **من الإدارة نفسها** (`managerOf` يشترط `department_id` مطابقًا). ولا ينقل الملكية في أي انتقال. وبطاقة `CRM-HANDOVER` (تسليم فرصة مكسوبة للتشغيل) في `business-dev`، وبطاقة `ACC-BRIEF-INTAKE` في `accounts`: أي أن الدليل يفترض ضمنيًا القراءة الأولى. و`client_links` هو الجسر بين `clients` و`commercial_cases`. |
| **التوصية (مقترح)** | القراءة الأولى، مع إضافة صريحة: تُسجَّل الحسابات **مراقبًا إلزاميًا** على العرض قبل الإرسال لا معتمدًا له. هذا يحفظ وحدة المسؤولية عن الرقم ويمنع مفاجأة مدير الحساب. |
| **من يقرر** | الرئيس التنفيذي أو نائب الرئيس للنمو والقنوات — لأن الإدارتين تحت قطاع واحد (`GROWTH`) والقرار يمسّ تفويضًا. |

### CF-02 — التنفيذ قبل الدفع، أم ترتيب المخطط

| | |
|---|---|
| **القراءة الأولى** | المخطط يرتّب: عقد ← دفعة مقدمة ← استلام مشروع ← انطلاق. ولا يبدأ تنفيذ قبل تأكيد المالية استلام المقدَّم (MOD-PM-01). |
| **القراءة الثانية** | الواقع التشغيلي يبدأ التنفيذ فور التوقيع، والدفعة تلاحق. |
| **أثر الأولى** | حماية نقدية حقيقية، ولا عمل بلا غطاء. وتأخير في بدايات المشاريع، واحتكاك مع عملاء حكوميين وكبار تستغرق دوراتهم المالية أسابيع. |
| **أثر الثانية** | سرعة، وتعرّض مباشر: عمل منفَّذ بلا تحصيل، وهو أخطر ما يصيب وكالة. |
| **ماذا يقول الكود اليوم** | **القراءة الثانية مطبّقة بلا قيد.** `commercial.mjs:271` `create_project` يشترط عقدًا وعرضًا معتمدًا وأعضاء فريق، **ولا يستشير المالية إطلاقًا**. وفي الوقت نفسه اللبنة جاهزة: `advance_invoices` و`confirm_advance` في `billing-recurring.mjs` بفصل مسؤوليات، وبطاقة `FIN-CLIENT-INVOICE` تعرف حالة «دفعة مقدمة حسب العقد». |
| **التوصية (مقترح)** | لا تُحسم بـ«نعم» أو «لا»، بل ببوابة قابلة للتجاوز الموثّق: `create_project` يطلب تأكيد مالية، وإن غاب يُفتح المشروع **بحالة «تنفيذ بلا غطاء»** تحتاج اعتماد مفوّض أعلى وتظهر في لوحة المالية حتى تُغلق. هذا يحفظ السرعة ويجعل التعرّض مرئيًا ومحسوبًا بدل أن يكون صامتًا. **حدّ التفويض الذي يسمح بالتجاوز ليس لي أن أضعه.** |
| **من يقرر** | الرئيس التنفيذي بالاشتراك مع مدير المالية. القرار مالي بالدرجة الأولى. |

### CF-03 — ازدواج الرمزين MOD-01 وMOD-02

| | |
|---|---|
| **القراءة الأولى** | الرمزان مستعملان لنموذجين مختلفين في إدارتين مختلفتين، والازدواج خطأ ترقيم يُصحَّح بإعادة الترميز. |
| **القراءة الثانية** | الرمزان نسختان من نموذج واحد تطوّر، وإحداهما ملغاة عمليًا. |
| **أثر الأولى** | تصحيح الترقيم يكسر أي إحالة قديمة في مستندات الشركة ورسائلها. |
| **أثر الثانية** | إلغاء نسخة قد يُسقط حقولًا تستعملها إدارة فعلًا. |
| **ماذا يقول الكود اليوم** | لا وجود لأي من الرمزين في المستودع. المنصة تستعمل فضاء ترميز مختلفًا تمامًا (`CRT-DESIGN`, `ACC-BRIEF-INTAKE`, …) وتفرض **تفرّد الرمز** داخل الدليل. فأي ازدواج في المصدر سيُرفض عند التحميل. |
| **التوصية (مقترح)** | **لا تُنقل رموز المصدر إلى المنصة كمفاتيح.** يُعطى كل نموذج معرفًا داخليًا ثابتًا، ويُحفظ رمز المصدر (أو رمزاه) في حقل **أسماء بديلة** متعدد القيم. هكذا يعمل البحث بالرمزين معًا، ولا يُكسر أي إحالة تاريخية، ولا يُطلب من أحد أن يختار. القرار عن «أي الرمزين الصحيح» يصير قرار توثيق لا قرار نظام. |
| **من يقرر** | مالك دليل النماذج (مكتب الرئيس التنفيذي أو الحوكمة) — قرار توثيقي لا تشغيلي. |

### CF-04 — تسمية VD / PROD / CW

| | |
|---|---|
| **القراءة الأولى** | الثلاثة أسماء لثلاث وحدات عمل متمايزة: إنتاج مرئي (VD)، إنتاج عام (PROD)، كتابة محتوى (CW). |
| **القراءة الثانية** | VD وPROD اسمان لشيء واحد اختلفت تسميته بين وثيقتين، وCW وحده متمايز. |
| **أثر الأولى** | ثلاثة مسارات ورموز وسلاسل اعتماد. دقة أعلى، وعبء أعلى، واحتمال أن تجد إدارتان نفسيهما على النموذج نفسه. |
| **أثر الثانية** | بساطة، وخطر ضياع تمايز حقيقي بين إنتاج الفيديو وإنتاج الفعاليات. |
| **ماذا يقول الكود اليوم** | المنصة حسمت هذا بطريقتها: **إدارة واحدة** `production` تغطي `PRO-SHOOT` و`PRO-EVENT` و`PRO-EDIT-REVIEW` و`PRO-DELIVERY`، وكتابة المحتوى منفصلة تحت `creative` (`CRT-CONTENT`، `CRT-TRANSLATION`). وفي `agency.mjs` عائلات الخدمة الست عشرة تفصل `production` عن `events` عن `content_social`. أي أن الكود يقول: الإنتاج واحد إداريًا ومتعدد في عائلات الخدمة. |
| **التوصية (مقترح)** | تثبيت ما في الهيكل المعتمد: `PROD` إدارة واحدة، و`VD` **عائلة خدمة** داخلها لا إدارة، و`CW` يبقى تحت الخدمات الإبداعية. هذا يوافق الهيكل المعتمد في 26 أغسطس 2026 ولا يخترع تنظيمًا جديدًا. |
| **من يقرر** | مدير الإنتاج ومدير الخدمات الإبداعية، بمصادقة نائب الرئيس للنمو والقنوات. |

### CF-05 — فرع الاشتراكات في طلب العروض بلا أمر شراء

| | |
|---|---|
| **القراءة الأولى** | الاشتراكات المتكررة (أدوات، منصات، تراخيص) تُستثنى من دورة RFQ وأمر الشراء لأن التنافس فيها بلا معنى. |
| **القراءة الثانية** | الاستثناء ثغرة: الإنفاق المتكرر هو الأخطر، لأنه يتراكم بلا مراجعة ويتجدد تلقائيًا. |
| **أثر الأولى** | خفة تشغيلية حقيقية. وفتح باب: أي شراء يُسمّى «اشتراكًا» يفلت من الضوابط. |
| **أثر الثانية** | انضباط كامل، وعبء سخيف على تجديد أداة بمئتي ريال شهريًا. |
| **ماذا يقول الكود اليوم** | لا فرع اشتراكات في `procurement.mjs`. الدورة واحدة للجميع: ثلاثة عروض ثم ترسية ثم أمر ثم استلام ثم مطابقة ثلاثية. وتوجد بطاقة `ADM-SUBSCRIPTION` (تجديد اشتراك أو عقد خدمة) — **لكنها تحت مكتب الرئيس التنفيذي لا تحت المشتريات**. أي أن الفرع موجود تنظيميًا خارج المشتريات، وهذا بذاته خلل. ويقابله في سجل العقود نوع `retainer` و`software_license` مع تنبيهات مدد إشعار. |
| **التوصية (مقترح)** | لا استثناء من **التسجيل**، واستثناء من **المنافسة** فقط: الاشتراك يُسجَّل في سجل العقود بمورد مؤهَّل وتاريخ تجديد ومدة إشعار، ويُعفى من شرط الثلاثة عروض عند التجديد بالشروط نفسها، ويعود إلى الدورة الكاملة عند أي تغيّر في السعر أو النطاق. وتنتقل ملكية البطاقة إلى المشتريات. **حدّ القيمة الذي يفصل «تجديد بالشروط نفسها» عن «تغيّر جوهري» يضعه مدير المشتريات، لا أنا.** |
| **من يقرر** | مدير المشتريات ومدير المالية. |

### CF-06 — بوابة العقد في PR-03

| | |
|---|---|
| **القراءة الأولى** | لا نشاط علاقات عامة ولا مؤثرين قبل عقد موقّع مع الطرف الثالث. |
| **القراءة الثانية** | التنسيق والترشيح والتفاوض تسبق العقد بطبيعتها، والبوابة تقع عند **النشر** لا عند البدء. |
| **أثر الأولى** | حماية قانونية وحقوق استخدام مضمونة. وشلل: لا يمكن ترشيح مؤثر ولا حجز مقابلة قبل عقد. |
| **أثر الثانية** | واقعية تشغيلية. وخطر: مادة تُنتَج وتُنشَر بحقوق غير محسومة، وهو أكثر ما يُكلف الوكالات. |
| **ماذا يقول الكود اليوم** | **المنصة اختارت القراءة الثانية بصرامة.** `influencers.mjs` يمشي `draft → internal_review → active → completed`، ويسمح بالترشيح والتفاوض مبكرًا، ثم يضع البوابة عند **الدفع** عبر `paymentGate()` بخمسة موانع: الارتباط غير نشط، المؤثر غير مربوط بمورد، المورد غير مؤهَّل، لا حساب بنكي متحقَّق ساري، وإثبات التنفيذ البشري ناقص عن الموعود. وقبلها `INF-CONTENT-APPROVAL` تمنع النشر بلا اعتماد. وهذه هندسة جيدة. |
| **التوصية (مقترح)** | تثبيت ما بناه الكود ووصفه صراحة في المخطط: بوابتان لا واحدة — **بوابة النشر** (اعتماد داخلي ثم عميل) و**بوابة الدفع** (`paymentGate`). ويُضاف مانع سادس مقترح: لا نشر قبل تسجيل نطاق حقوق الاستخدام ومدته (WF-073)، لأن هذا هو الخطر الذي تقصده القراءة الأولى فعلًا. |
| **من يقرر** | مدير العلاقات العامة والمؤثرين، بمراجعة الحوكمة والالتزام. |

### CF-07 — قيمة «جولتان»

| | |
|---|---|
| **القراءة الأولى** | جولتان مجانيتان **سياسة شركة** تسري على كل عقد ما لم يُنص على خلافها. |
| **القراءة الثانية** | جولتان **قيمة قالب** فقط: افتراض يظهر في النموذج ويُعدَّل لكل عقد. |
| **أثر الأولى** | وضوح للعميل والفريق، وسهولة قياس التجاوز. وجمود: مشروع هوية ومنشور اجتماعي لا يستويان في جولتين. |
| **أثر الثانية** | مرونة تجارية، وضياع مرجع: إن كان كل عقد يحدد رقمه، فما معنى «مجاني» أصلًا؟ ويصعب بناء تنبيه موحّد. |
| **ماذا يقول الكود اليوم** | **القراءة الثانية مطبّقة.** `revisions` حقل لكل بند بنطاق 0–20 في ثلاثة مواضع مستقلة (`commercial.mjs`، `campaigns.mjs`، `estimates.mjs`) **بلا قيمة افتراضية**. ويميّز الدليل مصدر الملاحظة: بطاقة `CRT-REVISION` تسأل «العميل أم مراجعة داخلية» وتعلّل «ملاحظات العميل تُحسب على جولات التعديل في العقد، والداخلية لا». |
| **التوصية (مقترح)** | القراءة الثانية، مع شرط: القيمة الافتراضية تُخزَّن في **عرض الخدمة** (`offerings`) لا في الكود، فتختلف باختلاف العائلة، ويظل كل عقد قادرًا على تجاوزها بتسجيل. وتُلزَم كل بند بقيمة صريحة — لا يُسمح بترك الحقل فارغًا — حتى لا يوجد بند بلا سقف. |
| **من يقرر** | المدير الإبداعي ومدير الحسابات معًا (الأول يتحمل الكلفة والثاني يبيع الوعد). |

### CF-08 — تعليق منصة X: 100–150 كلمة أم 280 حرفًا

| | |
|---|---|
| **القراءة الأولى** | 100–150 كلمة هو المعيار التحريري للشركة، ويُقسَّم النص على سلسلة منشورات. |
| **القراءة الثانية** | 280 حرفًا هو حدّ المنصة، والمعيار التحريري يجب أن يحترمه. |
| **أثر الأولى** | اتساق نبرة ومحتوى عبر القنوات. وإنتاج نص لا يُنشر كما كُتب. |
| **أثر الثانية** | صلاحية فورية للنشر. وفقر في المحتوى الطويل الذي تحتاجه قنوات أخرى. |
| **ماذا يقول الكود اليوم** | لا حدود منصات إطلاقًا. `campaigns.mjs` يعرف **إحدى عشرة قناة** (منها `x`) و**ثماني صيغ**، و`content_items` لا تحمل حدًا ولا تتحقق منه. و`studio.mjs` يعرف قائمة قنوات أخرى ويحصر المخرج في قنوات البريف المعتمد. أي أن القنوات معرَّفة مرتين بقائمتين مختلفتين، وأيٌّ منهما بلا حدود. |
| **التوصية (مقترح)** | التعارض ظاهري لا حقيقي: 100–150 كلمة معيار **المحتوى الطويل**، و280 حرفًا حدّ **المنشور المفرد على X**. الحل ليس اختيار أحدهما، بل تخزين **حدّ لكل قناة وصيغة** في مرجع واحد (توحيد قائمتي القنوات أولًا)، والتحقق منه قبل الجدولة لا بعدها. القيم نفسها يضعها المدير الإبداعي. |
| **من يقرر** | المدير الإبداعي ومدير التسويق الرقمي. والقيم ليست سياسة مالية فلا تحتاج تصعيدًا. |

### CF-09 — مهلة العرض 1–2 ساعة مقابل مهلة التحقق المالي يوم عمل

| | |
|---|---|
| **القراءة الأولى** | المهلتان تخصّان شيئين مختلفين: العرض المبدئي السريع (1–2 ساعة) شيء، والتحقق المالي قبل أمر الشغل (يوم عمل) شيء آخر، فلا تعارض. |
| **القراءة الثانية** | تعارض حقيقي: إن كان العرض يحتاج تحقق المالية، فلا يمكن أن يصدر في ساعتين والمالية مهلتها يوم. |
| **أثر الأولى** | تحتاج فصلًا صريحًا بين مستندين: «عرض مبدئي» بلا التزام مالي، و«عرض نهائي» بعد التحقق. وإن لم يُفصلا، وعدتَ العميل بساعتين وسلّمته في يومين. |
| **أثر الثانية** | تسوية إحدى المهلتين. رفع العرض إلى يوم يفقد ميزة تنافسية حقيقية؛ وخفض المالية إلى ساعتين يعني تحققًا شكليًا. |
| **ماذا يقول الكود اليوم** | **المنصة تناقض المهلتين معًا.** `defaultTargetDays` في `service-catalog.mjs` (سطور 970–979) يعطي بادئة `CRM-` **سبعة أيام عمل**، وبادئتي `FIN-` و`PRC-` **سبعة أيام عمل**. فلا 1–2 ساعة ولا يوم واحد. وهذه أول قيمة في المنصة تناقض المصدر مناقضة صريحة لا فجوة. ومحرك الاعتماد يصعّد بعد 24 ساعة مرة واحدة فقط. |
| **التوصية (مقترح)** | القراءة الأولى، بشرط تسمية المستندين تسمية مختلفة في النظام وفي ما يصل العميل: **«تقدير مبدئي»** يصدر سريعًا وعليه بيان صريح بأنه غير ملزم وغير متحقَّق ماليًا، و**«عرض سعر»** بعد التحقق. ثم تُصحَّح قيم `defaultTargetDays` لتوافق ما يُعتمد. بغير هذا الفصل، الالتزام بالمهلتين معًا مستحيل حسابيًا. |
| **من يقرر** | نائب الرئيس للنمو والقنوات ومدير المالية معًا. وهو **أعجل قرار في القائمة**، لأن ثلاثة صفوف في المصفوفة (WF-019, WF-081, WF-012) موقوفة عليه. |

### CF-10 — متابعة الفاتورة الضريبية بعد السداد

| | |
|---|---|
| **القراءة الأولى** | الفاتورة الضريبية تصدر **بعد** السداد بوصفها إثبات قبض، فتُتابَع لاحقًا. |
| **القراءة الثانية** | الفاتورة تصدر **قبل** السداد بوصفها مطالبة، والمتابعة بعدها للتحصيل لا للإصدار. |
| **أثر الأولى** | تتفق مع بعض أعراف الدفعات المقدمة. وتخالف الترتيب المحاسبي المعتاد: العميل عادة لا يدفع بلا فاتورة. |
| **أثر الثانية** | ترتيب سليم محاسبيًا. ويحتاج ضبطًا خاصًا للدفعات المقدمة. |
| **ماذا يقول الكود اليوم** | **القراءة الثانية مطبّقة بإحكام.** السلسلة: مخرج مقبول ← `ar_claims` (استحقاق) ← اعتماد ← `tax_invoices` ← إصدار بمسلسل وسلسلة بصمات (`chain_index`, `previous_hash`) ورمز QR بصيغة TLV ← `ar_receipts` (قبض). و`invoices.mjs:191` يرفض الإصدار إن لم يعد الاستحقاق معتمدًا. وADR-012 يفصل الاستحقاق عن الفاتورة عن القبض. أما الدفعة المقدمة فلها مسار منفصل في `billing-recurring.mjs` تُسجَّل فيه **التزامًا (إيرادًا مؤجلًا) لا إيرادًا**، ومعها تحذير ثابت لا يُحذف: معالجة الدفعات المقدمة في الفاتورة الإلكترونية لها متطلب خاص في مواصفة هيئة الزكاة والضريبة والجمارك، وما في المنصة سجل داخلي لا يصلح أساسًا للإصدار الفعلي. |
| **التوصية (مقترح)** | القراءة الثانية، وهي المطبّقة. والمتابعة بعد السداد تُفهم على أنها **مطابقة القبض بالفاتورة** لا إصدار متأخر. ويبقى مسار الدفعة المقدمة على حاله حتى يؤكد المختص الضريبي المعالجة الصحيحة — **وهذا التأكيد شرط، لا توصية**. |
| **من يقرر** | مدير المالية، وبشأن الدفعات المقدمة تحديدًا: المختص الضريبي المعتمد للشركة. |

## 2. تعارضات إضافية وجدتُها في المستودع

كل واحد منها موثّق بدليله. وهي لم ترد في قائمة المالك، وأرى أنها تستحق قرارًا.

### CF-11 — قائمتا قنوات مختلفتان لنفس الشركة

| | |
|---|---|
| **الدليل** | `campaigns.mjs`: `CHANNELS` إحدى عشرة قناة (`instagram, x, tiktok, snapchat, linkedin, youtube, google_ads, website, email, outdoor, other`). `studio.mjs`: قائمة قنوات أخرى (`instagram, x, linkedin, tiktok, youtube, website, internal, print, video, event`). القائمتان تتقاطعان ولا تتطابقان: `snapchat` و`google_ads` و`email` و`outdoor` في الأولى فقط؛ `internal` و`print` و`video` و`event` في الثانية فقط. |
| **القراءة الأولى** | الاختلاف مقصود: قنوات **النشر** غير قنوات **المخرج الإبداعي**. |
| **القراءة الثانية** | الاختلاف سهو، ويجب توحيدهما. |
| **الأثر** | المخرج الذي يُنتج لقناة في `studio` قد لا تكون له قناة مقابلة في `campaigns`، فيُكسر الربط بين الإنتاج والنشر، ويستحيل قياس «ما أُنتج مقابل ما نُشر». وهو أيضًا ما يمنع حلّ CF-08 (حدود المنصات) لأنه لا مرجع واحد يُعلَّق عليه الحد. |
| **التوصية (مقترح)** | مرجع قنوات واحد بحقلين: «صالحة للنشر» و«صالحة كمخرج»، فتبقى التفرقة المقصودة ويختفي الازدواج. |
| **من يقرر** | مدير التسويق الرقمي والمدير الإبداعي. |

### CF-12 — ساعة عمل أسبوعية افتراضية بلا سند

| | |
|---|---|
| **الدليل** | `agency.mjs` سطر 232: `weekly_hours ?? 40` عند غياب عقد توظيف نشط. وفي المقابل `resourcing.mjs` يرفض الافتراض صراحة: لا أسبوع 40 ساعة افتراضيًا، والسعة رقم يدخله المالك بسنده، وبغيره **لا سعة**. |
| **القراءة الأولى** | الافتراض تسهيل عرضي في لوحة الاستغلال لا أثر له على قرار. |
| **القراءة الثانية** | أي رقم يظهر في لوحة يُتخذ عليه قرار، ولو لم يُقصد ذلك. والوحدتان تتناقضان في المبدأ نفسه. |
| **الأثر** | نسبة استغلال محسوبة على مقام مخترع تبدو صحيحة وليست كذلك، وقد تُستعمل في تسعير أو في حكم على أداء. |
| **التوصية (مقترح)** | تعميم مبدأ `resourcing.mjs` على `agency.mjs`: لا رقم بلا سند، وتُعرض «غير محسوبة» بدل 40. وهذا يوافق ما تفعله المنصة أصلًا في الهامش حين تغيب التكلفة (`الهامش غير محسوب لأن التكلفة غير متاحة`). |
| **من يقرر** | مدير الموارد البشرية ومدير المشاريع. وهو قرار مبدأ لا قرار رقم. |

### CF-13 — العتبات تنبّه ولا توقف

| | |
|---|---|
| **الدليل** | `media-spend.mjs`: تجاوز العتبة **يوجب إقرارًا مكتوبًا بقرار** (`continue / reduce / pause_requested`) و**لا يوقف حملة**، والتعليق صريح في الكود. وفي المقابل `procurement.mjs:204` يوقف الترسية فورًا عند تجاوز المخصص (`budget_exceeded`). |
| **القراءة الأولى** | الفرق مقصود: الإنفاق الإعلامي يمرّ على حساب العميل ويضرّ إيقافه المفاجئ بالحملة والعميل معًا؛ أما المخصص الداخلي فحدّ صلب. |
| **القراءة الثانية** | تناقض في فلسفة الضبط داخل النظام نفسه: بوابة صلبة هنا وإقرار ناعم هناك، بلا قاعدة معلنة تفسّر متى أيّهما. |
| **الأثر** | إن لم تُعلن القاعدة، فسّرها كل فريق على هواه، وصار الإقرار المكتوب إجراءً شكليًا يُنقر عليه. |
| **التوصية (مقترح)** | إعلان القاعدة صراحة في دليل الشركة: الضبط الصلب حيث يقع الالتزام على **مال الشركة**، والإقرار الموثّق حيث يقع على **مال العميل بعلمه**. وإضافة تصعيد تلقائي للإقرارات المتكررة على الحملة نفسها. |
| **من يقرر** | مدير المالية ومدير التسويق الرقمي. |

### CF-14 — أعمار الذمم بلا شرائح

| | |
|---|---|
| **الدليل** | `receivables.mjs` يحسب حالات: غير مقدم، قيد الاعتماد، مرفوض، ملغى، متنازع عليه، متأخر، غير مستحق، مسدد داخليًا. **ولا شرائح 30/60/90 يومًا.** ومتطلب FIN-04 ينصّ على «أعمار ذمم». |
| **القراءة الأولى** | الحالة تكفي، والشرائح تفصيل تقريري يُضاف لاحقًا. |
| **القراءة الثانية** | «أعمار الذمم» بلا شرائح ليست أعمارًا، وإجراء المتابعة يختلف جوهريًا بين متأخر عشرة أيام ومتأخر تسعين. |
| **الأثر** | متابعة تحصيل بلا تدرّج: كل متأخر يُعامَل معاملة واحدة، فيضيع الجهد على الصغير ويُترك الكبير. |
| **التوصية (مقترح)** | إضافة شرائح وإجراء متابعة لكل شريحة. **حدود الشرائح وإجراءاتها يضعها مدير المالية؛ 30/60/90 عرف شائع لا سياسة لهذه الشركة، ولن أقدّمه على أنه كذلك.** |
| **من يقرر** | مدير المالية. |

### CF-15 — رمز المصدر لا موضع له في الدليل

| | |
|---|---|
| **الدليل** | بطاقات `service-catalog.mjs` تحمل `code` و`name_ar` و`name_en` و`req` (ربط بالمتطلبات الـ220)، **ولا تحمل حقلًا لرمز المصدر** (FRM-0xx أو MOD-xx-xx). |
| **القراءة الأولى** | رموز المصدر تاريخية، والمنصة ترميزها الخاص يكفي. |
| **القراءة الثانية** | الموظف الذي سيستعمل المنصة يعرف نماذجه برموزها القديمة، ولن يجدها. |
| **الأثر** | فجوة تبنٍّ مباشرة: نموذج يعرفه الفريق باسم MOD-BD-01 لن يظهر في البحث بهذا الاسم. وهي أيضًا العقبة العملية أمام حل CF-03. |
| **التوصية (مقترح)** | حقل «أسماء بديلة» متعدد القيم على كل بطاقة، يُفهرَس في البحث، يحمل رمز المصدر واسم الملف والاسمين العربي والإنجليزي. رخيص التنفيذ، وأثره في التبنّي كبير. |
| **من يقرر** | مالك دليل النماذج. قرار منخفض المخاطر. |

## 4. ما لا يحسمه هذا السجل

- نصوص التعارضات العشرة كما كتبها المالك حرفيًا. **ما لديّ وصفها لا نصها**، فقد أكون أخطأتُ في فهم أحدها. المراجعة قبل الاعتماد ليست شكلية.
- أي رقم أو حدّ أو مهلة. حيث ظهرت حاجة إلى رقم، سمّيتُ من يضعه ولم أضعه.
- التعارضات التي قد تكون داخل الملحق نفسه ولم أرَها، لأن الملحق لم يصلني.
